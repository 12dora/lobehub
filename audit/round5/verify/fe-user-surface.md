### fe-user-surface-D5-1 — CONFIRMED

- **What the original claimed:** Managed Connector settings hide the implemented `PlatformConnectorAuthorization` surface, leaving users unable to authorize organization-published `per_user_oauth` Connectors.

- **What I actually found:** The personal and workspace routes both render `ManagedConnectorSettings` ([personal route:3-8](</Users/konata/code/AIHub/src/routes/(main)/settings/connector/index.tsx:3>), [workspace route:3-8](</Users/konata/code/AIHub/src/routes/(main)/[workspaceSlug]/settings/connector/index.tsx:3>)). That wrapper explicitly delegates to `ManagedResourceBoundary` ([ManagedConnectorSettings.tsx:12-20](/Users/konata/code/AIHub/src/features/PlatformConnectorAuthorization/ManagedConnectorSettings.tsx:12)), which returns `ManagedResourceNotice` whenever Connectors are managed ([ManagedResourceBoundary.tsx:17-23](/Users/konata/code/AIHub/src/features/ManagedResources/ManagedResourceBoundary.tsx:17)).

  The authorization component contains the only end-user Connect/Reconnect actions ([ConnectorCard.tsx:138-165](/Users/konata/code/AIHub/src/features/PlatformConnectorAuthorization/ConnectorCard.tsx:138)) and calls the authorization hook ([PlatformConnectorAuthorization.tsx:45-47](/Users/konata/code/AIHub/src/features/PlatformConnectorAuthorization/PlatformConnectorAuthorization.tsx:45), [PlatformConnectorAuthorization.tsx:127-138](/Users/konata/code/AIHub/src/features/PlatformConnectorAuthorization/PlatformConnectorAuthorization.tsx:127)). A production-only repository search found no caller of `PlatformConnectorAuthorization`; it is merely exported at [index.ts:1-2](/Users/konata/code/AIHub/src/features/PlatformConnectorAuthorization/index.ts:1).

- **Refutation attempts:**

  - Checked every settings route and router registration. Personal settings dynamically loads the cited connector route ([componentMap.ts:71-76](</Users/konata/code/AIHub/src/routes/(main)/settings/features/componentMap.ts:71>)); both desktop workspace router variants register only the cited workspace route ([desktopRouter.config.tsx:826-831](/Users/konata/code/AIHub/src/spa/router/desktopRouter.config.tsx:826), [desktopRouter.config.desktop.tsx:697-700](/Users/konata/code/AIHub/src/spa/router/desktopRouter.config.desktop.tsx:697)). No dedicated authorization route exists.
  - Checked the notice’s Browse alternative. It routes Connectors to `/community/mcp` ([managedResourcePresentation.ts:11-20](/Users/konata/code/AIHub/src/features/ManagedResources/managedResourcePresentation.ts:11)), whose action invokes the legacy `installMCPPlugin` flow ([ActionButton/index.tsx:33-58](</Users/konata/code/AIHub/src/routes/(main)/community/(detail)/mcp/features/Sidebar/ActionButton/index.tsx:33>)). It never invokes the enterprise authorization client.
  - Checked the enterprise client seam. `startAuthorization` is exposed at [enterpriseAdapter.ts:45-58](/Users/konata/code/AIHub/src/features/PlatformConnectorAuthorization/enterpriseAdapter.ts:45), but its only production use is the unreachable hook at [useConnectorAuthorizationActions.ts:49-88](/Users/konata/code/AIHub/src/features/PlatformConnectorAuthorization/useConnectorAuthorizationActions.ts:49).
  - Checked organization-shared OAuth as an alternative. The admin control only designates the current user’s existing authorizations as shared ([SharedOAuthAuthorizationControl.tsx:92-118](/Users/konata/code/AIHub/src/enterprise/client/features/admin/managedResources/SharedOAuthAuthorizationControl.tsx:92), [SharedOAuthAuthorizationControl.tsx:180-189](/Users/konata/code/AIHub/src/enterprise/client/features/admin/managedResources/SharedOAuthAuthorizationControl.tsx:180)); it does not create a binding.
  - Checked runtime fallback. A `per_user_oauth` execution loads an exact binding ([runtimeAdapter.ts:244-276](/Users/konata/code/AIHub/apps/server/src/enterprise/services/connectorCatalog/runtimeAdapter.ts:244)) and rejects missing, stale, revoked, or mismatched bindings ([runtimeAdapter.ts:467-493](/Users/konata/code/AIHub/apps/server/src/enterprise/services/connectorCatalog/runtimeAdapter.ts:467)). Runtime does not initiate authorization.
  - Checked tests. The component test constructs an artificial `/settings/connector` route containing the component directly ([PlatformConnectorAuthorization.test.tsx:94-105](/Users/konata/code/AIHub/src/features/PlatformConnectorAuthorization/PlatformConnectorAuthorization.test.tsx:94)). The production-route test only asserts that both source files contain the managed wrapper and fallback ([componentMap.sync.test.ts:26-39](</Users/konata/code/AIHub/src/routes/(main)/settings/features/componentMap.sync.test.ts:26>)).
  - Checked baseline scope. At `4bab163640`, the authorization and managed-resource feature trees did not exist, and the settings action rendered ordinary `ToolSettings` directly at `4bab163640:src/routes/(main)/settings/connector/index.tsx:5-7`. This is fork-owned, not an inherited upstream defect.

- **Verdict rationale:** No route, registry, dynamic import, marketplace action, runtime fallback, or admin control reaches the only binding-creation UI. The defect is independently reproduced.

- **Corrected severity and scope:** **HIGH.** It affects enterprise deployments using platform-managed Connectors and published `per_user_oauth` Connectors when the effective user or shared owner lacks a pre-existing valid binding. Credential-free and `shared_service_account` Connectors are unaffected; previously established valid bindings may continue working.

### fe-user-surface-D5-2 — DOWNGRADED

- **What the original claimed:** A later settings update aborts an earlier request while persisting only its own top-level groups, allowing the earlier edit to be lost and then overwritten by server refresh.

- **What I actually found:** `setSettings` optimistically merges each edit into the complete local override state ([action.ts:89-105](/Users/konata/code/AIHub/src/store/user/slices/settings/action.ts:89), [action.ts:189](/Users/konata/code/AIHub/src/store/user/slices/settings/action.ts:189)). It then constructs the request exclusively from top-level keys in that invocation’s `changedFields` ([action.ts:191-200](/Users/konata/code/AIHub/src/store/user/slices/settings/action.ts:191)). Creating the next request aborts the previous controller ([action.ts:72-81](/Users/konata/code/AIHub/src/store/user/slices/settings/action.ts:72)), and the narrowed payload is sent with that signal ([action.ts:202-205](/Users/konata/code/AIHub/src/store/user/slices/settings/action.ts:202)).

  Therefore, after optimistic `{ memory: … }`, a subsequent `{ general: … }` request contains only `general`. If the first dispatched request is canceled before reaching persistence, the database never receives `memory`. The successful second request calls `refreshUserState`, whose SWR success handler replaces—not merges—the store’s settings with server data ([common/action.ts:115-167](/Users/konata/code/AIHub/src/store/user/slices/common/action.ts:115)).

- **Refutation attempts:**

  - Checked transport batching. Settings mutations use `httpBatchLink` ([lambda.ts:145-155](/Users/konata/code/AIHub/packages/trpc/src/client/lambda.ts:145)). Same-tick operations can share a batch, whose request aborts only after every constituent signal aborts ([signals.ts:4-31](/Users/konata/code/AIHub/node_modules/@trpc/client/src/internals/signals.ts:4)). This prevents loss for some overlaps, but not when the first single-operation batch has already dispatched before the second edit aborts its sole signal ([httpBatchLink.ts:54-76](/Users/konata/code/AIHub/node_modules/@trpc/client/src/links/httpBatchLink.ts:54)).
  - Checked whether an aborted fetch necessarily cancels server work. It does not: a request already accepted by the server can still commit. That narrows the vulnerable timing window but does not protect a request canceled before server acceptance.
  - Checked database and policy guards. The ordinary persistence path updates only supplied top-level columns ([user.ts:268-278](/Users/konata/code/AIHub/packages/database/src/models/user.ts:268)). The managed-policy transaction similarly processes only leaves present in the request and writes only the resulting partial ([effectiveSettingsService.ts:752-785](/Users/konata/code/AIHub/apps/server/src/enterprise/services/settings/effectiveSettingsService.ts:752), [effectiveSettingsService.ts:829-858](/Users/konata/code/AIHub/apps/server/src/enterprise/services/settings/effectiveSettingsService.ts:829)). Transactions and locks cannot restore an omitted canceled group.
  - Checked for a client dirty-group queue, per-group controller, revision, or CAS. None exists around [action.ts:189-215](/Users/konata/code/AIHub/src/store/user/slices/settings/action.ts:189).
  - Checked reachability. The same Service Model form exposes `defaultAgent` and `systemAgent` updates through the same global action and save-state helper ([ModelAssignmentsForm.tsx:28-73](/Users/konata/code/AIHub/src/features/ServiceModel/ModelAssignmentsForm.tsx:28)); those controls can issue overlapping writes from distinct top-level groups ([ModelAssignmentsFormView.tsx:154-191](/Users/konata/code/AIHub/src/features/ServiceModel/ModelAssignmentsFormView.tsx:154)).
  - Checked the regression test. It changes two fields inside `general`, so the second payload contains the already-merged first edit, and it mocks `refreshUserState` to a no-op ([action.test.ts:152-184](/Users/konata/code/AIHub/src/store/user/slices/settings/action.test.ts:152)). It does not exercise the reported cross-group persistence outcome.
  - Checked baseline scope. Baseline sent the complete `diffs` object in every request at `4bab163640:src/store/user/slices/settings/action.ts:189-193`. The narrowed top-level payload and rollback logic are fork changes, so this is not out of scope.

- **Verdict rationale:** The race is real, but the original severity overstates its consistency and blast radius. Same-batch requests or requests already executing server-side commonly preserve the first edit. A loss requires a cross-group overlap during the cancellable window, and the affected data is a user preference that can be re-entered.

- **Corrected severity and scope:** **MEDIUM.** Affects overlapping writes to different top-level user-settings groups when the earlier request is canceled before persistence. The outcome is a silent, recoverable preference/configuration loss; no durable user content, authorization boundary, or organization-wide state is corrupted.
