## Findings

**F1 (high) — `pendingRestart` is computed against the env-only fallback, not the real boot snapshot.**
`getPendingRestartModules()` (`apps/server/src/enterprise/services/moduleSettings/index.ts:336`) diffs
`getBootModules()` against the effective map. In the request path `bootModules` is still `null`, so
`getBootModules()` returns `envOnlySnapshot().effective` — the value `initBootModules()` sets inside
`instrumentation.register()` is not visible to the tRPC handlers (separate module instance under Next
standalone). Evidence on the live container: after the restart that applied `bots=false` from the DB
(proved by `[modules] worker gatewayService skipped`), `GET /trpc/lambda/admin.modules.get` returns
`"pendingRestart":[]` and every row shows 运行中 — i.e. the operator is told the bots gateway is running
when the process booted without it; conversely, right after saving 标准 (before any restart) the banner
counted 2 because env-only said `bots=true`. Both symptoms are the same bug, and the false negative is
the dangerous half: re-enabling a restart-kind module gives no restart prompt at all.
Repro: `curl -s 'http://localhost:3024/trpc/lambda/admin.modules.get?input=%7B%22json%22%3Anull%7D' -H "cookie: …"`.

**F2 (medium) — `POST /api/agent/gateway/start` does not early-return when `bots` is off.**
Expected (PLAN S8) 200 `{disabled:true}`; observed `401 {"error":"Unauthorized"}` on standard *and* minimal
(and the same 401 on full, so the auth check runs before any module gate). Functionally closed, but the
documented contract and the "never a hard error for a disabled module" rule are not met.

**F3 (medium) — `userMemory.getPersona` is called on every page even when `memory` is off**, so minimal shows
2 console errors (`403` + `TRPCClientError: PLATFORM_MODULE_DISABLED`) on **every** admin page and on the
user chat home. Exact request:
`GET /trpc/lambda/userMemory.getPersona?batch=1&input=…` → 403 `PLATFORM_MODULE_DISABLED`.
This is the only cause of the two "0 console errors" failures on minimal. `memory` has no derived
FEATURE_FLAG (S10 only derives knowledge_base / ai_image / speech_to_text / market), so the client hook is
never told to stand down. Fix: gate the hook on `useModuleEnabled('memory')` (or derive a flag).

**F4 (low, pre-existing / environment) — network proxy settings in `lobechat_perf` cannot be decrypted.**
`[network-proxy] settings load failed; serving last-known-good or default { errorClass: 'Error' }` on every
tier at boot, and `/admin/system/general?tab=network-proxy` on standard renders 「无法读取当前状态」/「无法读取安装状态」
with `TRPCClientError: PLATFORM_CONFIG_VALIDATION_FAILED` (`shots/standard_admin_system_general-tab=network-proxy.png`).
It reproduces independently of the tier, so it looks like stored data in this DB copy rather than a slim
regression — worth one confirmation against `lobechat_demo` before release.

**F5 (low, UX) — `/admin/system/general?tab=network-proxy` on minimal** (networkProxy off) silently falls back
to the 基础设施 tab: no error, but also no 「模块未启用」 explanation for the link the operator followed.
Matches F1's documented tab-fallback design; flagging only as a copy gap.

**Note (not a defect)** — the runtime first-screen measurement (242 JS files / 25.46 MB decoded, via
`performance.getEntriesByType('resource')`) is above the §7 ≤22 MB target. F2's 21.78 MB counts only the
entry + `modulepreload` set; the extra ~3.7 MB is route chunks the chat home pulls in afterwards. Same
number on all three tiers — module gating does not change what the browser downloads.
