## 3. Load comparison (20 concurrent streaming chats × 2 min, same DB, fake OpenAI on `host.docker.internal:8899`)

Provider wired server-side (`OPENAI_API_KEY` + `OPENAI_PROXY_URL`) so the real `/webapi/chat/openai` path is
exercised; one chat verified end-to-end first (SSE `event: text` tokens). An admin poll loop
(`admin.overview.getSummary` / `system.getInstances` / `modules.get` every 5 s) stands in for the admin tab.
Fake stream = 200 tokens over 2.0 s, so ~0.55 s of the latency is the app.

| tier | CPU p50 / p95 | RSS start → peak | DB xact/s | latency p50 / p95 | requests | errors |
|---|---|---|---|---|---|---|
| full | 23.9 % / 27.4 % | 374 → **647 MB** | 23.4 | 2546 ms / 2570 ms | 960 | 0 |
| minimal | 21.1 % / 28.9 % | 376 → **551 MB** | 22.8 | 2544 ms / 2572 ms | 960 | 0 |

Reading: at 20 concurrent streams the two tiers are indistinguishable on CPU, throughput (960 completed
streams each, 0 errors) and latency; the difference is **~96 MB of resident memory** (−15 %). That matches
the design — module gating removes boot-time graph and background jobs, not per-message work on the paths a
chat actually uses. Idle remains where the win is (V1: 271 → 214 MB, 8 fewer workers, 0.53 → 0.33 xact/s).
Caveat: `moderation` is off in minimal, and its per-message cost is only visible with rules configured —
this run had none, so the per-message column is a floor, not a ceiling.
