## Levers built and measured — each moved 0 bytes

1. **Manual chunk groups for `@lobehub/icons` / `elkjs`+`beautiful-mermaid` / `katex`.** With
   `strictExecutionOrder: true`, rolldown will not split a statically executed module out of the
   shared chunk that already executes it: no `vendor-mermaid` / `vendor-katex` chunk was emitted at
   all, and `vendor-icons-brand` *swallowed* the separate antd chunk (7.40 + 1.29 → one 9.81 MB
   chunk) with blocking JS unchanged at 25.70 MB. Same mechanism as F2's `vendor-syntax`
   duplication. **Groups only pay off for code that is already dynamic-only.** Reverted.
2. **`elkjs` / `beautiful-mermaid` marked side-effect-free** via a `resolveId` plugin (neither
   declares `sideEffects:false`, so one `THEMES` constant drags 2.6 MB). No change: the module is
   needed eagerly (`THEMES`) *and* lazily (the renderer), so it stays in the eager chunk. The edge is
   `@lobehub/ui/es/Markdown/components/CodeBlock.mjs` → `Mermaid` → `hooks/useMermaid.mjs` →
   `beautiful-mermaid` → `elkjs/lib/elk.bundled.js`. **Upstream `@lobehub/ui` item.** Reverted.
3. **`@lobehub/icons` made fully lazy — the big one, and it does not work.** Escalating attempts, all
   measured: (a) `React.lazy` on the 12 first-screen call sites + `registerBrandIconsAsync()` (the
   registries via `await import()`) — eager chunk byte-identical, 7,758,732 B; (b) all **53** call
   sites off the barrel onto `es/features/*` subpaths — byte-identical again; (c) a bundler alias
   swapping the `@lobehub/icons` barrel for a slim shim so `es/features/index.js` left the graph
   entirely (it is pulled by ~30 first-screen `@lobehub/ui` modules: `LogoMono`, `EmojiPicker`, every
   auth-provider `Avatar`) — `features/providerConfig` reached **zero** static importers outside the
   package, dynamic-only, and the eager chunk still came out 7,626,371 B on three consecutive builds
   with `AlephAlpha` (an icon reachable *only* through the registry) still inside it; (d) collapsing
   the four `React.lazy` calls onto one dynamic boundary module (four dynamic chunks sharing
   `providerConfig` let rolldown hoist it into the common chunk) — byte-identical; (e) naming just
   those six modules as a group — **hung `rendering chunks` for >9 min**, killed. Everything reverted
   (58 files restored via a scoped `git apply -R`; no `git checkout/reset/stash/add` was used).
   Conclusion: this needs a rolldown chunking fix or an upstream `@lobehub/icons` change.

## Findings the commander should act on (none are mine to fix)

1. **Nothing in the repo registers the service worker.** `injectRegister: null` and no
   `serviceWorker.register` / `registerSW` / `virtual:pwa-register` anywhere (`src`, `apps`,
   `scripts`, templates). So the 76 MB precache was never actually downloaded by a client — my fix
   removes a dead 1525-entry manifest and a landmine for whenever registration is added, not a live
   76 MB download. Worth a decision: either wire registration up (now safe) or drop VitePWA.
2. **`chat-*` 2.23 MB is 34.5 % `mathjs` + 8.4 % `nerdamer-prime` + `decimal.js`**, from
   `packages/builtin-tool-calculator/src/executor/index.ts` — on the eager chat graph. **G1's file**;
   an `await import()` in that executor is worth ~1 MB of first-screen JS.
3. **`i18n-default-index` 1.62 MB eager is 70 % `packages/model-bank/src`**, not locale data — the
   `providerConfig` group for model-bank did not hold it. Same rolldown merge behaviour as (1) above.
4. **`ErrorContent-*` 1.17 MB is 25 % `pdfjs-dist` + 17 % `lodash`.** `routeChunkPreload` correctly
   keeps pdfjs chunks out of the *preload list*, but the chunk is still fetched as a static import of
   a chunk that IS preloaded — `isPrewarmExcludedChunk` cannot stop that.
5. **Decision for you, not shipped:** `desktop-chat-launch` (`includeDynamicImports: true`) adds

   `<link modulepreload>` to the existing idle phase would take blocking JS 25.67 → 21.20 MB, at the

# Round 3 — review rework (`REVIEW_F4.md`: PASS, 2 MAJOR)

## #1 MAJOR (coupled loaders) — fixed

`packages/builtin-tool-calculator/src/executor/index.ts`: one `ensureMathLibs()` became two
independent single-flight loaders, `ensureMathJs()` and `ensureNerdamer()`. Each method awaits only
what it uses — `calculate` / `evaluate` → mathjs; `solve` / `differentiate` / `integrate` /
`defintegrate` / `execute` / `limit` → nerdamer; **`sort` and `base` await nothing** (they use
`@thi.ng/base-n` and plain JS). Verified by reading every method body: no nerdamer path touches
`math.` or `formatResult`, and `sort` touches neither library. So a mathjs-only call no longer
downloads 0.47 MB of nerdamer (or fails on its load error), and vice versa. The reviewer was right
that they are two chunks, not one — the comment now says so.

## #2 MAJOR (precache offline shell) — reverted, per verdict

`vite.config.ts` restored to HEAD (`git checkout --`, the only change in that file);
`plugins/vite/pwaPrecache.test.ts` deleted. Precache is back to **1530 entries / 74.2 MB**.
**Keep in mind, so nobody re-fights this:** that precache is *dormant* — nothing in the repo
registers a service worker (`injectRegister: null`, and no `serviceWorker.register` / `registerSW` /
`virtual:pwa-register` call exists anywhere in `src`, `apps`, `scripts` or the templates), so no
client ever downloads it. If registration is ever wired up, narrowing `globPatterns` is **not**
enough on its own: a newly installed worker does not control the requests of the load that installed
it, so `runtimeCaching` cannot backfill the entry's static closure — the precache must be derived
from that closure (plus the active locale) or the offline shell breaks. `sharedRendererConfig.ts`
never referenced the PWA config, so nothing was recorded there.
