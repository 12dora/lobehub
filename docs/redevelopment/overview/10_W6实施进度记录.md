## 3. Runtime、Inbox 与 Rollout 闭环

- Agent 发布、归档和依赖读取在同一锁命名空间内协调；运行时只解析 operation 固化的 exact historical revision /version/checksum，缺失、漂移或 partial binding 均 fail closed，不回落 latest。
- 平台 operation 的 start binding、human-intervention kind、resume anchor 与 fingerprint 由服务端产生；approval /reject/tool-result 使用事务 CAS 单赢家消费。升级前 ordinary operation 保留 legacy 行为，Flag 关闭不增加平台目录读取。
- `default-inbox` 仅覆盖稳定 builtin Inbox 的受管可见配置和执行快照，不复制第二个 Inbox；历史 topic /message/session 继续关联原 identity。托管 runtime 清除未 pin 的 prompt /tool side channel，paused resume 先复核实时 entitlement，再精确重放旧版本。
- Rollout worker 每批最多 100 个目标，在事务内复核 parent、lease、control revision、Assignment scope 和 checksum；transition ledger 固化真实 previous proof，mixed /null/drift 无法反向 rollout。默认 inbox 回滚继续切换 publication pointer，自动化回归覆盖该兼容路径。
- rollout cohort 以 PostgreSQL `transaction_timestamp()` 冻结严格六位 UTC 微秒 cutoff，字符串全链路不经 JavaScript `Date`；用户和角色成员边界均在 SQL 中 cast 为 `timestamptz`。前端只轮询去重后的 active job id（每轮最多 20 个），终态停止。
