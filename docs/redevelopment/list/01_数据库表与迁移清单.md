## 2. Migration 顺序

1. **Migration 0 / Expand：** 创建 M01 公共表与全部业务空表，所有新列可空或有安全默认值，不改变现有行为。
2. **Migration 1 / RBAC：** 插入平台权限、固定角色和超级管理员种子；先不启用 Guard。
3. **Migration 2 / Settings：** 建策略/Override，运行 Shadow Resolver；不改用户设置。
4. **Migration 3 / AI：** 导入或创建 Provider/Model Draft，发布测试 Catalog。
5. **Migration 4 / Skill/Connector：** 迁移定义，Token/Secret 单独处理。
6. **Migration 5 / Agent：** 建模板/版本/Assignment，不批量创建用户 Agent。
7. **Migration 6 / Identity/Branding：** 配置 Draft，OIDC 未重启前不激活。
8. **Contract 清理：** 至少经过一个稳定版本后，才评估清理旧路径或无用字段。

## 3. 数据库设计规则

- 所有平台表使用独立前缀 `platform_`，避免与上游核心表语义混淆。
- ID 使用仓库现有 `createNanoId`/`idGenerator` 约定。
- Secret 不写 Revision JSON 和 Audit Diff；存 `secret_ref`、fingerprint 和 configured 状态。
- 每个外键明确 `onDelete`；发布历史通常采用 restrict/soft archive，不级联删除。
- 列表查询必须有游标索引；禁止依赖 OFFSET 处理大用户量。
- Migration 必须在空库和脱敏生产快照运行，检查锁时长、索引创建和回滚兼容。
